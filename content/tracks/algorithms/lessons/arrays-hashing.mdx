## Intuition

Most brute-force solutions repeat the same question inside a loop — "have I seen x?", "how many times does y appear?" — and each answer costs O(n). A hash set or map answers in O(1) on average, turning O(n²) into O(n).

If that notation is new: O(n) means the work grows in step with the input, so 10 times the data takes about 10 times as long. O(1) means the work stays about the same at any size. O(n²) means 10 times the data takes 100 times as long. [Complexity & Big-O](/cs-fundamentals/complexity/) explains this properly.

Think of a coat check: instead of searching every coat, you hand over a ticket and get your coat instantly. The hash map is the coat check; the key is the ticket. Under the hood, a **hash function** turns the key into a bucket number, so the lookup goes straight to one bucket. "On average" matters: if many keys landed in one bucket, that bucket would have to be searched. Good hash functions make this rare.

Four shapes cover most problems:

- **Seen set / map**: Contains Duplicate, Two Sum (store what you've seen, look up what you need).
- **Counter**: Valid Anagram, Top K Frequent.
- **Group by key**: Group Anagrams — pick a key that is identical for everything in a group.
- **Prefix sum + map**: Subarray Sum Equals K — `sum(i..j) = prefix[j + 1] - prefix[i]`.

**Prefix sums.** A subarray (a contiguous slice) can be summed in O(1) if you prepare running totals first. Let `prefix[i]` be the sum of the first `i` values, with `prefix[0] = 0`:

```text
nums    =     [3, -1, 4, 2]
prefix  =  [0, 3,  2, 6, 8]

sum of nums[1..3] = prefix[4] - prefix[1] = 8 - 3 = 5     (-1 + 4 + 2)
```

Everything before the slice cancels out. Building the table is one O(n) pass, and each query after that is one subtraction. In the Template's map version, a slice ending here sums to `k` exactly when some earlier running total equals `prefix - k`, so it counts those totals in a map. That works with negative numbers, where a sliding window doesn't.

**Prefix products.** The same running idea works for multiplication. Start at 1 and multiply as you go. For `[2, 3, 4, 5]`, the table is `[1, 2, 6, 24, 120]`, and each entry is the product of everything before that position. A pass from the right gives everything after it. A range product is `prefix[j + 1] // prefix[i]`, as long as no zero is involved: one zero turns every later entry into 0, and the division then fails.

**When not to use it.** A hash map remembers values but keeps no useful order, so it can't answer "what is the smallest?" or "what is the next bigger?". It also costs O(n) extra memory. If the input is sorted, or memory is tight, look further before reaching for one.

**Telling it from its neighbours.** Use **Two Pointers** when sorted order tells you which candidates to discard. Use **Sliding Window** when the answer is one contiguous block and growing it only pushes the condition one way. Use a hash map when you need to look up earlier values by what they are, wherever they sit.

## Template

```python
from collections import Counter, defaultdict


def two_sum(nums: list[int], target: int) -> tuple[int, int] | None:
    seen: dict[int, int] = {}              # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:             # check BEFORE inserting x
            return seen[target - x], i
        seen[x] = i
    return None


def group_by_signature(words: list[str]) -> list[list[str]]:
    groups: defaultdict[tuple[str, ...], list[str]] = defaultdict(list)
    for w in words:
        groups[tuple(sorted(w))].append(w)  # lists aren't hashable; tuples are
    return list(groups.values())


def count_subarrays_with_sum(nums: list[int], k: int) -> int:
    count = prefix = 0
    seen = Counter({0: 1})                 # empty prefix
    for x in nums:
        prefix += x
        count += seen[prefix - k]
        seen[prefix] += 1
    return count
```

## Example

**The problem.** A market stall keeps a ledger in time order. A positive number is a charge for that amount; a negative number is a refund. Each refund must cancel one earlier charge of the same amount that hasn't been refunded yet. Return the positions of the refunds with no such charge, so someone can check them by hand.

**Spotting the pattern.** For every refund we ask "have I seen this amount before?", and we need to know how many are still open. Those are two triggers: a lookup inside a loop, and counting frequencies.

**Why brute force is slow.** The direct way scans back through the ledger for an unused charge at every refund. With 100,000 lines, half of them refunds, that can mean 50,000 scans of up to 100,000 lines each, up to 5 billion steps. That is O(n²).

**The key insight.** We never need the old lines themselves, only how many charges of each amount remain open. Keep that in a counter, and each line costs one O(1) update.

```python
from collections import Counter


def unmatched_refunds(ledger: list[int]) -> list[int]:
    open_charges: Counter[int] = Counter()     # amount -> charges not yet refunded
    orphans: list[int] = []
    for i, amount in enumerate(ledger):
        if amount > 0:
            open_charges[amount] += 1
        elif open_charges[-amount] > 0:
            open_charges[-amount] -= 1         # cancels one earlier charge
        else:
            orphans.append(i)
    return orphans
```

**Traced run** on `[5, 12, -5, 7, -12, -7, -5, 9]`:

| i | amount | Action | Open charges | Orphans |
|---|---|---|---|---|
| 0 | 5 | new charge | 5×1 | none |
| 1 | 12 | new charge | 5×1, 12×1 | none |
| 2 | -5 | cancels a 5 | 12×1 | none |
| 3 | 7 | new charge | 12×1, 7×1 | none |
| 4 | -12 | cancels a 12 | 7×1 | none |
| 5 | -7 | cancels a 7 | empty | none |
| 6 | -5 | no open 5 | empty | 6 |
| 7 | 9 | new charge | 9×1 | 6 |

The answer is `[6]`. The second refund of 5 has nothing left to cancel. Eight lines took eight O(1) updates, and the 100,000-line ledger would take about 100,000 rather than billions.

## Complexity

- Time: **O(n)** average for one pass with O(1) lookups. Sorting-based keys add O(k log k) per item of length k.
- Space: **O(n)** for the map or set.

## Pitfalls

- Two Sum: inserting `x` before checking pairs an element with itself.
- Using a list as a dict key — convert to a tuple (or a 26-count tuple).
- Prefix sums: forgetting the `{0: 1}` base case misses subarrays that start at index 0.
- Prefix tables: mixing up `prefix[j + 1] - prefix[i]` with `prefix[j] - prefix[i]`, which drops the last element.
- Assuming hashing is always O(1) — fine for interviews, but say "average case".

## Tips & tricks

- `Counter(a) == Counter(b)` checks anagrams in one line.
- A tuple of 26 letter counts costs O(k) per word against O(k log k) for `sorted(word)`, which matters for long strings.
- Longest Consecutive Sequence: put everything in a set and only start counting at numbers whose `x - 1` is missing.
- If extra memory is forbidden and the input is sorted, think **Two Pointers** instead.
- Reading a missing key from a `Counter` returns 0 and doesn't add the key; a plain `dict` raises `KeyError`.
