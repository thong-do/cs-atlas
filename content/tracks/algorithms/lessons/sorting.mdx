## Intuition

You must sort a pile of exam papers by surname. Give half to each of two helpers to sort, then merge their piles by always taking whichever top paper comes first. That's **merge sort**. Or pick one paper, put every surname before it on the left and every one after it on the right, and repeat on each side. That's **quicksort**.

Sorted data answers questions cheaply: duplicates become neighbours, binary search works, and [Two Pointers](/algorithms/two-pointers/) can walk inwards.

**Merge sort.** Split in half, sort each half with a recursive call, then merge. A merge makes at most one comparison per item it places. Halving gives about log₂ n levels, and each level merges n items in total, so merge sort costs O(n log n) on every input. It needs O(n) extra memory.

**Quicksort and partitioning.** Pick a **pivot**, then **partition**: rearrange the range so everything smaller than the pivot comes first, then the pivot, then the rest. The pivot is now in its final place, and each side is sorted the same way. It sorts in place, with no second list.

**Quicksort's worst case.** If the pivot is always the smallest or largest value, each partition peels off one item, and the work is n + (n − 1) + … ≈ n²/2. A first-item pivot does exactly this on already sorted input. A **random pivot** makes it very unlikely on any input, for an expected O(n log n), though the worst case is still O(n²). Many equal values are a separate trap: the template sends every item equal to the pivot to the right, so identical values are quadratic even with a random pivot. Splitting three ways, into smaller, equal and larger, fixes that.

**Quickselect.** To find the k-th smallest item once, partition as quicksort does, then continue only into the side that holds position k. On average the range shrinks by a constant fraction each time, so the expected total is O(n), with the same O(n²) worst case as quicksort.

**Stability.** A sort is **stable** if items with equal keys keep their original order. That matters when the existing order means something: sort orders by time, then stably by customer, and each customer's orders stay in time order. Merge sort is stable when ties are taken from the left half (`<=` in the merge). The quicksort template isn't: a long-distance swap can carry an item past an equal one.

**Counting sort.** When the values are whole numbers from 0 to k − 1, skip comparisons. Count how many times each value appears, then write the values out in order. That's O(n + k) time and O(k) extra memory: better than O(n log n) when k isn't much bigger than n, and hopeless when k is a billion.

**The lower bound.** Any sort that learns about order only by comparing two items needs at least log₂(n!) comparisons in the worst case. n distinct items have n! possible orders. Each comparison splits the orders still possible into two groups, and in the worst case the answer leaves the bigger group, at least half. log₂(n!) grows like n log₂ n, so comparison sorts are Ω(n log n). For 10 items, log₂ 3,628,800 ≈ 21.8, so none can promise fewer than 22 comparisons. It's about the worst case: Python sorts an already sorted list with n − 1 comparisons. And counting sort escapes it, because it uses values as list indexes instead of comparing them.

**When to just call `sort()`.** Almost always. Python's `list.sort()` and `sorted()` use Timsort, a merge sort hybrid written in C: O(n log n) in the worst case, about n comparisons on sorted input, and stable. `key=` sorts by anything, such as `key=len` or a tuple `key=lambda o: (o.customer, o.time)` for several keys. The key is computed once per item, not per comparison, and `reverse=True` still keeps equal items in their original order. Write your own when the algorithm is the task, when the merge does useful work (as in the Example), or when you need the O(n) of quickselect or counting sort, as interviews often ask. In plain Python the C-coded `sort()` can still win on the clock, so measure. For a rule that compares two items directly, wrap it with `functools.cmp_to_key` and pass it as the `key`.

**Telling it from its neighbours.** A [Heap](/algorithms/heap/) hands you the current smallest while items come and go, and the k smallest without ordering the rest. [Binary Search](/algorithms/binary-search/) needs sorted data but doesn't make it: sort once, then search as often as you like.

## Template

```python
import random


def merge_sort(a: list[int]) -> list[int]:
    if len(a) <= 1:
        return a[:]
    mid = len(a) // 2
    left, right = merge_sort(a[:mid]), merge_sort(a[mid:])
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:          # ties come from the left: stable
            out.append(left[i])
            i += 1
        else:
            out.append(right[j])
            j += 1
    return out + left[i:] + right[j:]


def partition(a: list[int], lo: int, hi: int) -> int:
    """Rearrange a[lo..hi] around a random pivot; return the pivot's final index."""
    p = random.randint(lo, hi)
    a[p], a[hi] = a[hi], a[p]            # move the pivot to the end
    i = lo                               # a[lo:i] holds items smaller than the pivot
    for j in range(lo, hi):
        if a[j] < a[hi]:
            a[i], a[j] = a[j], a[i]
            i += 1
    a[i], a[hi] = a[hi], a[i]            # the pivot goes right after them
    return i


def quicksort(a: list[int], lo: int = 0, hi: int | None = None) -> None:
    if hi is None:
        hi = len(a) - 1
    if lo < hi:
        p = partition(a, lo, hi)
        quicksort(a, lo, p - 1)
        quicksort(a, p + 1, hi)


def quickselect(a: list[int], k: int) -> int:
    """The k-th smallest value, counting from 0. Reorders a."""
    lo, hi = 0, len(a) - 1
    while True:
        p = partition(a, lo, hi)
        if p == k:
            return a[p]
        if p < k:
            lo = p + 1
        else:
            hi = p - 1


def counting_sort(nums: list[int], k: int) -> list[int]:
    """Every value must be in range(k)."""
    count = [0] * k
    for x in nums:
        count[x] += 1
    return [v for v in range(k) for _ in range(count[v])]
```

## Example

**The problem.** Two judges rank the same bakers in a contest. Number the bakers by judge A's ranking, then list them in judge B's order. For example, `[4, 1, 5, 2, 6, 3]` means B put A's 4th baker first. Two bakers are a **disagreement** if the judges put them in opposite orders. How many disagreements are there?

**Spotting the pattern.** A disagreement is a pair where a bigger number comes before a smaller one, and a sorted list has none. `sort()` would throw away how items moved, so the count has to come from inside a merge.

**Why brute force is slow.** Checking every pair is O(n²): about 5 billion pairs for 100,000 bakers.

**The key insight.** Let the recursive calls count the disagreements inside each half, and count the ones between halves during the merge. When the merge takes an item from the right half, every item still waiting in the left half is bigger and came earlier, so each forms one crossing disagreement. So add how many are waiting. That costs what merge sort costs, about 100,000 × 17 ≈ 1.7 million steps.

```python
def count_disagreements(ranks: list[int]) -> int:
    def sort_count(a: list[int]) -> tuple[list[int], int]:
        if len(a) <= 1:
            return a, 0
        mid = len(a) // 2
        left, inside_left = sort_count(a[:mid])
        right, inside_right = sort_count(a[mid:])
        merged, i, j, crossing = [], 0, 0, 0
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:
                merged.append(left[i])
                i += 1
            else:
                merged.append(right[j])
                j += 1
                crossing += len(left) - i      # it jumps every left item still waiting
        merged += left[i:] + right[j:]
        return merged, inside_left + inside_right + crossing
    return sort_count(ranks)[1]
```

**Traced run** on `[4, 1, 5, 2, 6, 3]`. The halves `[4, 1, 5]` and `[2, 6, 3]` hold one disagreement each (4 before 1, 6 before 3). The final merge of the sorted halves:

| Left waiting | Right waiting | Takes | Crossing added |
|---|---|---|---|
| 1, 4, 5 | 2, 3, 6 | 1 from left | 0 |
| 4, 5 | 2, 3, 6 | 2 from right | 2 |
| 4, 5 | 3, 6 | 3 from right | 2 |
| 4, 5 | 6 | 4 from left | 0 |
| 5 | 6 | 5 from left | 0 |

The left half is then empty, so 6 is copied over. That's 4 crossing disagreements plus 2 inside the halves, 6 in all, which matches checking all 15 pairs by hand.

## Complexity

- Merge sort: **O(n log n)** time on every input, **O(n)** extra space.
- Quicksort: **O(n log n)** expected with a random pivot, **O(n²)** worst case; in place, with a recursion stack O(log n) deep on average and O(n) at worst.
- Quickselect: **O(n)** expected, **O(n²)** worst case.
- Counting sort: **O(n + k)** time, **O(k)** extra space besides the output.
- Python's `sort()`: **O(n log n)** worst case, about n comparisons on sorted input.
- The Example: **O(n log n)** time, **O(n)** space.

## Pitfalls

- A first-item pivot on sorted input: O(n²) time, and n levels of recursion, which fails past about 1,000 items in Python. Pick the pivot at random.
- Many equal values with a two-way partition: quadratic even with a random pivot. Partition three ways.
- `<` instead of `<=` in the merge: the output is still sorted, but equal items from the right half jump ahead, so the sort is no longer stable.
- Sorting numbers stored as strings: `sorted(["10", "9"])` gives `["10", "9"]`, because strings compare character by character. Use `key=int`.
- `nums = nums.sort()` sets `nums` to `None`: `list.sort()` sorts in place and returns nothing. `sorted()` returns a new list.

## Tips & tricks

- Before anything clever, ask: "If this were sorted, could I solve it in one scan?"
- Several keys: one `key=` tuple, such as `(-p.score, p.name)` for highest score first and names A to Z on ties, or sort by the minor key and then stably by the major key.
- In an interview, name the sort and its cost: "the built-in sort, O(n log n), and it's stable."
