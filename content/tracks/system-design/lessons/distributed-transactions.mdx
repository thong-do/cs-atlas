## Intuition

At a wedding the officiant asks each partner "Do you?" and both say yes. Only then are they declared married. Once you have said yes you must wait for the declaration; if the officiant faints, both stand stuck until revived. That is **two-phase commit**.

Now plan a holiday: hotel, then car, then flight, with three companies. If the flight fails, nobody can roll back the hotel's database; you email to cancel, perhaps paying a fee. That is a **saga**.

**The problem.** An order must be recorded in the Orders database *and* paid in the Payments database. A normal transaction (isolation: see [Consistency models](/system-design/consistency-models/)) lives inside one database. With two, a crash between the commits leaves one done and one not. We want all or nothing.

**Two-phase commit (2PC).** A **coordinator** drives the **participants**.
1. **Prepare.** Each participant does the work, writes its changes durably, **keeps its locks** and votes YES (a promise that it can commit) or NO.
2. **Decide.** If all vote YES, the coordinator **durably logs COMMIT**. That log write is the **decision point**: the outcome is fixed even if everything crashes. Then it tells everyone to commit; any NO or missing vote means ABORT.

A participant that voted YES can no longer decide alone. The coordinator may already have logged COMMIT and told another participant, so aborting could split the outcome; it must **wait for the decision**, still holding its locks. So if the coordinator dies, participants block and others queue behind their locks.

On restart, a coordinator with a logged decision re-sends it. With none, many implementations use **presumed abort**: aborts need not be logged, and any inquiry with no record is answered ABORT. That is a common convention, not a law of the protocol.

2PC solves atomic commit, not consensus, and blocks on coordinator failure; variants such as three-phase commit and Paxos Commit aim to reduce that.

**XA** is a standard interface for running 2PC across databases and brokers; support and performance vary by product. Microservices usually avoid it for **availability** (all participants must be up), **coupling** and **lock time** (locks span round trips and coordinator outages).

**Sagas.** Garcia-Molina and Salem (1987) split a transaction into **local transactions** T1, T2, … each with a **compensating action** C1, C2, …. If a step fails, run the compensations of the completed steps in **reverse** order.
- A compensation is a **semantic undo**, not a rollback: the commit happened and others may have seen it. "Cancel booking" may leave a fee.
- Sagas give **atomicity (eventually), consistency and durability, but no isolation**: ACD without I.
- A compensation must be **safe to retry** and must **eventually succeed**, or be escalated to a human.
- The **pivot** is the go/no-go step. Steps before it are compensatable; steps after it are **retriable** and must eventually succeed. Put the hard-to-undo step as late as possible.

In **orchestration**, a central service tells each participant what to do next. In **choreography**, services react to each other's events: no central component, but a scattered flow.

Each step carries a **producer-assigned idempotency key**, and commands leave a service through the **outbox** from [Queues & streams](/system-design/queues-streams/), so a crash cannot lose them.

**The isolation problem.** Between steps, others see partial results, such as a hotel booked for a trip that fails. Mitigate with a **pending** status (a **semantic lock**): others treat the record as provisional.

**TCC (try-confirm-cancel)** is a related pattern. In most descriptions, each service offers a *try* that tentatively claims capacity, then a *confirm* or *cancel*. It builds in the pending state, but services must implement all three idempotently and expire unconfirmed tries (details vary).

```text
      │                 │
  C1 cancel hotel   C2 cancel car

 Happy path:  T1 → T2 → T3 → T4
 Car fails:   T1 ok, T2 fails or times out → C2 (no-op if never booked), C1
 After pivot: T3 ok, T4 fails → retry T4 until it succeeds (never undo T3)
```

## Example

A trip-booking saga with an orchestrator. Hotel and car cancel freely and the ticket is non-refundable, so the ticket is the pivot, third; the repeatable itinerary email follows.

| Step | Action | Compensation |
|---|---|---|
| T1 | Book hotel | Cancel hotel |
| T2 | Book car | Cancel car |
| T3 | Issue ticket (pivot) | none |
| T4 | Send itinerary | none: retry |

**When the car booking fails.** T1 has committed and T2 is refused. The orchestrator marks the saga `compensating`, runs C2 (a no-op if the car was never booked) then C1, and ends in `failed`; no ticket was issued. A car *timeout* is handled the same way. The service must remember a cancel against the step's booking key (`:undo` derives from it), so a late booking is rejected.

A timeout on the **pivot** is different: the ticket may exist, so the orchestrator never compensates blindly. It queries the ticket's status by key, or marks the saga `unknown` and escalates.

The sketch is generic, not any framework.

```python
import time

class StepFailed(Exception): ...      # definite refusal
class TransientError(Exception): ...  # timeout or 5xx: outcome unknown

def retry(fn, attempts=8):
    for i in range(attempts):
        try:
            return fn()
        except TransientError:
            if i == attempts - 1:
                raise                    # still unknown: caller escalates
            time.sleep(min(30, 2 ** i))

def run_saga(sid, before_pivot, pivot, after_pivot, store):
    """before_pivot: [(name, do, undo)]; pivot, after_pivot: (name, do)."""
    s = store.load(sid) or {"started": [], "done": [], "status": "running"}
    if s["status"] in ("failed", "completed", "unknown"):
        return s
    key = lambda name, sfx="": f"{sid}:{name}{sfx}"  # one key per step

    def step(name, do):
        if name not in s["started"]:
            s["started"].append(name)
        store.save(sid, s)               # persist BEFORE the call
        retry(lambda: do(idempotency_key=key(name)))
        s["done"].append(name)
        store.save(sid, s)

    if s["status"] == "running":
        try:
            for name, do, _ in before_pivot:
                if name not in s["done"]:
                    step(name, do)
            if pivot[0] not in s["done"]:
                try:
                    step(*pivot)
                except TransientError:   # ticket may exist
                    s["status"] = "unknown"   # query by key, or escalate
                    store.save(sid, s)
                    return s
        except (StepFailed, TransientError):  # refusal or unknown
            s["status"] = "compensating"
            store.save(sid, s)

    if s["status"] == "compensating":
        undo = {n: u for n, _, u in before_pivot}
        for name in reversed(s["started"]):  # reverse order
            if name in undo:
                retry(lambda: undo[name](idempotency_key=key(name, ":undo")))
        s["status"] = "failed"
        store.save(sid, s)
        return s

    for name, do in after_pivot:             # retriable
        retry(lambda: do(idempotency_key=key(name)))
    s["status"] = "completed"
    store.save(sid, s)
    return s
```

State is saved before every call, so a restart resumes, and each step's fixed key means a retry is not applied twice.

## Pitfalls

- **Treating 2PC as free.** A coordinator outage freezes locks. Fix: use it among systems you control, with short transactions.
- **Assuming a saga is isolated.** Readers see steps that later compensate. Fix: a pending status or semantic lock.
- **Compensating as if it were rollback.** Others saw the effect. Fix: design each compensation as a business action that may leave a trace.
- **Non-idempotent or silently failing compensations.** Fix: idempotent undo, backoff, human alert.
- **Pivot too early.** Fix: compensatable steps first, only retriable steps after.
- **A fresh idempotency key per retry.** The service applies it again. Fix: one persisted key per step.

## Tips & tricks

- 2PC for a few systems you control; a saga for independent services. First ask whether the data belongs in one service.
- Per step, write down its compensation, its key and its side of the pivot. Measure saga duration, stuck sagas, compensation failures and the oldest pending record.
- Interview phrasing: "A saga with an orchestrator: compensatable steps, a late pivot, then retriable steps, an idempotency key per step, and a pending status because sagas lack isolation."
