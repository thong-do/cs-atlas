## Intuition

A nightclub doorman does not let everyone in at once, nor lock the door for an hour. He admits a few people now, a few more as others leave, and tells the rest to wait. A **rate limiter** is that doorman for your API.

**Why limit:**
- **Protect capacity:** a runaway client or retry loop should not take everyone down.
- **Fairness:** one heavy user cannot starve the rest.
- **Cost:** calls to a paid downstream service stay bounded.
- **Abuse:** password guessing, scraping and credential stuffing become slow.

**The algorithms**, for a limit such as "100 requests per minute":
- **Fixed window:** count requests in each calendar minute and reset at the edge. Cheap (one counter), but it has a **boundary burst**: a client can send 100 requests in the last second of one window and 100 in the first second of the next. That is up to **2× the limit** within a short span straddling the edge.
- **Sliding window log:** store a timestamp per request and count those in the last 60 s. Exact, but memory grows with the limit, per key.
- **Sliding window counter:** keep the current and previous window counts and estimate: `previous × (1 − elapsed/W) + current`, where `elapsed` is the time into the current window and `W` the window length. It **approximates** by assuming the previous window's requests were spread evenly.
- **Token bucket:** a bucket of up to `capacity` tokens refills at `rate` tokens per second. Each request takes one token; with none left it is rejected. The **maximum burst is the capacity**, and the **long-run average cannot exceed the refill rate**. Over T seconds at most about `capacity + rate × T` requests pass.
- **Leaky bucket:** the name has two common meanings. One is a **queue that drains at a fixed rate**, which smooths output but adds waiting. The other is a **meter** that counts like a bucket filling and leaking, which behaves much like a token bucket.

**Choosing the key.** Limit per API key or authenticated user when you can. By IP address is a fallback with two traps. **NAT** puts many users behind one IPv4 address, so a shared limit punishes them all. **IPv6** gives one host many addresses (a typical home network gets a /64 or larger), so limit by a **prefix** such as /64 rather than the full address, or one host dodges the limit by rotating. Consider a coarser /56 or /48 limit as well, since ISPs often delegate those.

**Where to enforce.** An API gateway or load balancer rejects early and protects every service behind it. The application knows the plan and the endpoint's cost.

**Several instances.** A 100/min counter in each gateway's memory allows up to 100 × (number of instances) if requests spread evenly. Two fixes:
- **Shared store:** a store such as Redis, which every instance asks. Accurate, but adds a hop and a dependency.
- **Per-instance share:** give each instance `limit ÷ N`. No hop, but approximate: a client pinned to one instance gets only `limit ÷ N`, while one spread across all gets about the full limit. Recompute when N changes (autoscaling).

**Atomicity.** The naive version reads the count, adds one, writes it back. Two gateways can both read 99 and both write 100, letting 101 through. `INCR` is atomic, but `INCR` then `EXPIRE` as two commands has a gap: a crash in between leaves a counter that never expires. `MULTI` (or `SET key 0 EX 60 NX` then `INCR`) closes the `INCR`/`EXPIRE` gap only. To read and branch atomically, use a **Lua script**, which runs atomically on a single Redis node. In a Redis Cluster, all keys a script touches must hash to the same slot.

**Responses.** Reject with `429 Too Many Requests` and a `Retry-After` header, which is either a number of seconds or an HTTP-date. Informational headers vary: many providers use `X-RateLimit-*` names, but names and meanings differ. An IETF draft defines `RateLimit` and `RateLimit-Policy` header fields; it is still a draft.

**Client behaviour.** Honour `Retry-After`. Otherwise use **exponential backoff with jitter**: wait a random time up to `min(cap, base × 2^attempt)`, so thousands of clients do not retry in lockstep.

## Example

A token bucket for a login endpoint (illustrative limits: capacity 8, refill 0.5 tokens/s, i.e. 30 per minute sustained). It refills lazily: no timer, only arithmetic from elapsed time, with fractional tokens.

```python
import math
import threading
import time


class TokenBucket:
    def __init__(self, capacity=8, rate=0.5, clock=time.monotonic):
        self.capacity = float(capacity)
        self.rate = rate                  # tokens added per second
        self.clock = clock                # monotonic: unaffected by wall-clock changes
        self.tokens = self.capacity       # start full
        self.last = clock()
        self.lock = threading.Lock()      # one process; see Redis note below

    def allow(self, cost=1.0):  # returns (allowed, seconds_to_wait)
        with self.lock:
            now = self.clock()
            self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
            self.last = now
            if self.tokens >= cost:
                self.tokens -= cost
                return True, 0.0
            return False, (cost - self.tokens) / self.rate


buckets = {}  # one bucket per key; evict idle keys


def check(key):
    if key not in buckets:
        buckets[key] = TokenBucket()
    ok, wait = buckets[key].allow()
    return (200, {}) if ok else (429, {"Retry-After": str(math.ceil(wait))})
```

After 8 quick attempts the bucket is empty, and the ninth gets 429 with `Retry-After` rounded up to whole seconds. After 10 s idle, 5 tokens are back (10 × 0.5). This works inside one process only. Across gateways, move the same arithmetic into a **Lua script** that reads the bucket's `tokens` and `last` fields from one Redis hash, computes the refill, writes both back and sets an expiry on the key, all in one atomic call. Redis `TIME` gives one clock source; caller timestamps need NTP-synced gateways, and skew slightly mis-refills, so clamp elapsed with `max(0, now - last)`.

**Arithmetic check** on the visualizer's scenario. Of the 13 requests: 5 pass at t=0 (6, 7 and 8 are rejected), one each at t=1 and t=2, request 11 passes at t=3 but 12 is rejected, and request 13 passes at t=5 (the bucket held 1 at t=4, 2 at t=5). That is 9 allowed and 4 rejected; the bound 5 + 1 × 5 = 10 leaves 1 token unused.

## Pitfalls

- **Fixed-window only:** 2× at the edge; use a sliding window or bucket.
- **IP alone:** NAT and IPv6 rotation defeat it; key on API key or user.
- **Check-then-set races:** use an atomic `INCR` or a Lua script; `MULTI` alone can't branch on a value it read (that needs `WATCH` and a retry).
- **Per-instance counters taken as global:** N gateways allow roughly N× the limit.
- **No `Retry-After`:** clients guess and retry at once.
- **Silent limiter failure:** if Redis is down, decide on purpose: **fail open** (allow, risking overload) or **fail closed** (reject, risking an outage you caused). A coarse local fallback limit is a common middle path; for a login endpoint, closed may be safer.
- **A hot key:** one busy key sends all its checks to one Redis shard; cache rejections locally.

## Tips & tricks

- Describe the behaviour first: "steady 60/min with bursts of 10" is a token bucket with capacity 10 and refill 1 per second.
- Measure rejections per key, limiter latency and limiter-store errors.
- In interviews, state the trade-offs: exact (log) vs cheap (counter) vs bursty (bucket); shared accuracy vs local speed; fail open vs closed.
